Schema-First Extraction: Contract Intelligence Feed

Unstructured contracts in, reviewable evidence-backed records out — with uncertainty made visible instead of hidden

Why I Built This

My office work proves I can run AI programs inside an enterprise. This project is me proving something different: that I can define, build, and honestly evaluate an AI product from scratch — every decision mine, including the uncomfortable ones about what the numbers really support.

The Problem

Legal and Sourcing teams have the contract documents, but not a searchable view of what's inside them. Renewal deadlines get found manually. Liability terms can't be compared across a portfolio. And the sneaky one: when AI extraction doesn't show its uncertainty, a low-confidence guess looks exactly like a solid answer — and a missing clause looks the same as a clause the model failed to read.

The Product Decision

I wrote this rule down before writing any code, and it drove everything after:

"Start with the decisions users need to make, define the smallest reliable data contract that supports those decisions, and expand only when real usage and evaluation justify it."

So the goal was never to capture every sentence of every contract. It was a small set of high-value signals — renewals, liability, jurisdiction, indemnification — made visible at portfolio scale, with uncertainty explicit enough that a human knows what to trust and what to review.

Users & Decisions Served

  • Legal — risk review, liability comparison
  • Sourcing — renewal monitoring, notice periods
  • Both — jurisdiction analysis, review routing

Stack

  • Gemini API with Pydantic-typed structured JSON output
  • CUAD contract dataset for ingestion and evaluation
  • Configurable confidence threshold (0.70) for QC routing
  • JSONL persistence with resumable processing
  • Read-only dashboard: search, filters, renewal & jurisdiction views

How I Designed the Schema

The schema is the product here. I treated writing it the way I'd treat writing a PRD — meaning first, code later.

1. Start from user decisions, not contract concepts

I didn't list everything that appears in a contract. I listed the questions Legal and Sourcing actually ask — which contracts renew soon? which liability terms need review? — and only fields that support one of those questions made it in.

2. Three filters for every field

Business value (would it change an action?), extraction feasibility (can varied contract language produce it consistently?), and evaluation feasibility (can I actually check whether it's right?). A field had to pass all three.

3. Define meaning before writing code

Every field got a written definition: what it means, what a correct value looks like, what must not be inferred, and when null is the right answer. Example: termination_date means a fixed contractual end date — not a signature date, not a notice date. If the contract only grants termination rights, the value is null.

4. Make uncertainty a first-class output

The model is never forced to invent an answer. Clearly present → true. Clearly absent → false. Missing or ambiguous → null, with confidence and rationale attached either way. A missing value should never silently become a false one.

Every field returns the same shape

The model returns value, confidence, and rationale; a separate QC layer computes needs_review against the threshold. Four concepts, kept apart on purpose:

{ "value": "normalized value or null", "confidence": 0.82, "rationale": "One sentence grounded in the contract text.", "needs_review": false }

What the v1 Run Actually Showed

These are fixture-scale results — 5 contracts, 12 fields each, 60 field results — not production benchmarks. I'd rather report a small honest number than a big vague one.

76.67%

Auto-pass rate: 46 of 60 field results cleared the 0.70 confidence threshold.

23.33%

Routed to human review — which is the design working, not failing. The system refused to pass everything as trustworthy.

100% / 93.33%

Precision / recall on the 35 CUAD-labeled clause-presence decisions (F1 96.55%). Zero false positives — it never invented a clause.

Where it was strong

Governing law, jurisdiction, and assignment restriction: 100% auto-pass and perfect precision/recall on the fixture. Indemnification and confidentiality close behind at 80% auto-pass with perfect evaluation scores.

Where it was honest about being weak

Auto-renewal (60% auto-pass, one real case returned null because renewal language conflicted between the order form and an exhibit) and liability cap (40% auto-pass, one case returned unclear when multiple exclusions didn't fit the single-object schema). Ambiguous language is a real failure mode — the product response is review routing, not fake confidence.

Tradeoffs I Made on Purpose

Trustworthy over comprehensive

A small set of clearly defined fields beats a large set of vague ones. Liability caps got deliberately simplified to one normalized object — complex cases get flagged for review instead of forced into a misleadingly precise value.

Reviewability over false automation

Confidence, rationale, nulls, and review flags exist so an AI answer is never treated as automatically correct. The goal is reducing manual effort, not eliminating judgment.

Honest evaluation boundary

CUAD supports clause-presence evaluation, not exact dates or amounts — so I only claimed metrics where ground truth exists. No artificial accuracy scores for fields the dataset can't verify.

Static dashboard over backend

Read-only dashboard, CLI extraction, checked-in demo fixture. Proving the decision workflow didn't need auth, storage, and APIs — so v1 doesn't have them.

What I Learned as the Product Owner

  • A single aggregate accuracy number would have hidden the gap between reliable fields and review-heavy ones. Field-level metrics aren't optional.
  • High precision with a few missed positives beats confidently inventing clauses — but a missed auto-renewal is still an operational risk when the workflow is deadline-driven. I had to sit with that tension rather than pick a comfortable side.
  • The confidence threshold is a routing control, not an accuracy guarantee. A result can pass and still deserve domain review.
  • Five contracts can't support production claims, and saying so out loud is part of the job. The next step is a larger, independently reviewed sample — not a bigger marketing number.

What's Next

V2 — two scoped experiments, not broad iteration: a conflict-resolution rule for auto-renewal (with a conflict_detected flag, because two sections disagreeing is a finding, not a gap), and a test of whether liability caps need an array-shaped schema rather than a better prompt. Each has a decision rule and a 20-contract sample before trusting any delta.

MVP2 — source-agnostic platform: separate ingestion from domain schemas, add document-type routing, and validate HR audit as the first non-legal workflow — keeping confidence, rationale, and review routing as the cross-domain trust layer.

The Short Version

I defined the schema from the decisions Legal and Sourcing need to make, not from everything a contract contains. Every field has a meaning, a type, a null rule, and a line it must not cross on inference. The evaluation says something narrower than "the model understands contracts" — it says the tested presence signals are strong, ambiguous renewal and liability language genuinely isn't, and the review workflow catches what the model can't carry. That narrower claim is the one I can defend, which is exactly why I'm making it.
