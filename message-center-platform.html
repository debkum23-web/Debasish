01

Problem

Microsoft 365 Message Center advisories create real work: deprecations, security changes, compliance deadlines. Scrum masters, product owners, and leaders across our firm all need to catch the right ones in time.

What we had was a scheduled script that sent one email a day summarizing the last 24 hours. There was no history, and a critical advisory looked exactly like routine noise. Nothing connected an advisory to a person responsible for acting on it.

That was the untracked compliance risk. A deprecation or a security change could land, get buried in an inbox, and surface later as an incident. The messages that mattered most were the easiest to lose.

02

Product Decision

The obvious ask was "make the email better." I didn't think that was the fix. When I talked to the people reading it, the actual gaps were different, and those gaps became the spec: they couldn't look anything up after the fact, they couldn't tell at a glance what was urgent, and nothing tied an advisory to someone accountable for it.

01

Saying no to the stated request

Everyone wanted a better email. The job was to work out why the email could never work, and build for that instead.

02

Sequencing by usefulness

Queryable history first, then visual triage, then natural-language search, then Jira integration. Each release stood on its own, so if the project had stopped at any point people would still have had something better than before.

03

A wall between the LLM and the data

The LLM would never query the database. That guardrail was in the first design, not added after a security review.

04

Governance as a feature, not a checkbox

Access comes from identity, not a bolt-on login screen, so auditors can verify who saw what without asking us.

05

Closing the loop to an owner

"Advisory noticed" had to end in "ticket with an owner." That is the part that changes behavior, not just visibility.

03

Stakeholder Alignment

Two things had to be true before this could ship: leadership had to approve building it, and the people who would live in it had to want it. I took a different route to each.

01

Leadership — approval to build

I brought them the risk rather than a feature request: critical advisories could go untracked, and the only safeguard was a daily email. I secured their approval for an LLM-driven Message Center with natural-language search and one-click Jira remediation.

02

M365 admin leads and product managers — a working prototype

I showed them the prototype and walked through the dashboard against the email: flagged advisories at the top, full history, and no way for an advisory to be lost the way it can be in an inbox.

03

Security, compliance, and audit partners — designed in, not argued in

Because the LLM was walled off from the database and access came from identity from the first design, those conversations were short. Nothing had to be retrofitted.

04

Technical Approach

I owned the vision and roadmap, the data model, the API layer, the dashboard UX, the LLM search design, and access governance, and built the first working version myself.

Architecture — from API polling to a ticket with an owner

Scheduled Ingestion & Queryable Schema

A console app pulls Message Center data from Microsoft's APIs into SQL on a schedule. I designed the schema around the questions people actually ask ("when did this change?", "what else affected this service?") rather than just archiving raw payloads, so every past advisory stays searchable.

API Layer + Angular Dashboard

An 18-endpoint API layer feeds an Angular dashboard. Flagged messages sit at the top, visually separated from everything else. That one design choice fixed the thing the daily email never could.

LLM Search with Clarifying Follow-ups

Once people had history, filters stopped being enough. An LLM interprets a natural-language question, and if it's ambiguous it asks a follow-up instead of guessing. A separate search API runs the actual query, so the LLM never touches the database.

One-Click Jira Creation

Any flagged message becomes a Jira ticket in one click, pre-filled from the message data, with the ticket number shown back in the dashboard. Before this, tracking an advisory meant copy-pasting into Jira by hand, or more often not tracking it at all.

Identity-Governed Access

Login goes through Azure AD, and a UPN-to-permissions mapping decides what each person sees. Access control comes from identity, so audits can verify it.

06

Ongoing Ownership

Launch was the start of owning this, not the end of the project. I still own the product after launch, and what I hold myself to is below.

  • MVP 2 priorities. The roadmap after launch is mine to sequence, using the same rule as before: every release has to stand on its own.
  • The success measures. I defined how this platform is judged once it was live, so "did it work" isn't a matter of opinion.
  • The guardrails as it grows. Any new capability keeps the LLM away from the database and access tied to identity.
